What `openssl s_client -starttls smtp` sends: kit-c probe_smtp.sh against a fake SMTP server (2026-11-18)

Recorded on the laptop inside `unshare -Urn` (network namespace with loopback only; nothing left the machine).
Client: kit-c/probe_smtp.sh mx.example.test 127.0.0.1 2525 <label> <groups> <trace> probe.example.test 12, i.e.
  timeout 12 openssl s_client -connect 127.0.0.1:2525 -starttls smtp -name probe.example.test
          -servername mx.example.test -tls1_3 -groups <groups> -trace < /dev/null
  (OpenSSL 3.5.6 7 Apr 2026).
Server: kit-c/tests/fake_smtp.py on 127.0.0.1:2525 speaks the plaintext SMTP part itself and logs every byte the client
sends; after "220 Ready to start TLS" it relays the raw bytes to `openssl s_server -tls1_3 -www -naccept 1 -trace`
(s_server has no STARTTLS mode), whose trace shows what the client sent inside TLS after decryption.
The same facts are asserted by tests s01 and s02 of tests/test_kit.py at every run.

Summary
- Nothing is sent before the server's greeting (case tarpit: connection accepted, no byte from the client until the
  12 s timeout ended the probe).
- After the greeting the client sends exactly "EHLO <-name>\r\n", then exactly "STARTTLS\r\n", then the TLS handshake.
- Inside TLS the client sends only handshake messages and, because stdin is /dev/null, a close_notify alert; then it
  closes the TCP connection. No application data, no MAIL, RCPT, DATA, RSET or QUIT, before or after TLS.
- s_client does not look at SMTP reply codes: it sends EHLO after a 554 greeting, STARTTLS when the EHLO reply does not
  offer it (and prints "Didn't find STARTTLS in server response, trying anyway..."), and after a refused STARTTLS
  (454) it still sends its ClientHello (a binary TLS record, 243 bytes for P2) in plaintext; the server reads it as
  garbage command lines (here two "502" replies), s_client reports "wrong version number" and closes. That probe fails.
- s_client writes the last line of the server's EHLO reply into its output after a completed handshake ("250
  8BITMIME" below). It is server-controlled text inside the trace file (see README, SMTP section).
- HRR detection works on the STARTTLS trace: probe P2 against a default s_server gives hrr=1 grp=X25519MLKEM768.
